# 未知物品与自行车链路设计

日期：2026-10-15。性质：第 6 项的设计交付，不是已实现的装配引擎。当前游戏可制作固定物品，尚无自行车、关节、骑乘、传动、蓝图编辑器或作品分享服务。

## 1. 孩子做什么

“我想造一辆能骑的自行车” → 选已有的部件图卡 → 在场景中拖到可连接接口 → 看轮子是否能转、车把是否能转向 → 上车试用 → 改装 → 保存作品 → 下次继续。

孩子不必填写零件表、阅读长规则或先答题。接口用可连接/不可连接颜色、形状与短提示说明；不能做的行为明确提示“这个功能还没做好”，愿望和草稿仍保留。提供已支持实验作为可选分支，不把滑步车偷偷改名为自行车。

这是目标体验。本轮工坊仍为图卡与二维格子拖放，并非上述三维装配操作已经存在。

## 2. 六层链路

| 层 | 数据内容 | 判断职责 |
| --- | --- | --- |
| 知识与来源 | 来源 URL/核对日期、适用条件、真实事实/游戏约定/幻想标记 | 解释为什么，不直接执行自然语言 |
| 材料与工艺 | 材料属性、正常取得方式、工艺输入输出/条件/不可逆变化 | 判断材料是否确实存在、工艺是否可做 |
| 部件类型 | 几何、材质、碰撞形状、接口、行为能力、数据版本 | 决定这是轮子、轴还是仅有轮形外观 |
| 连接图 | 部件实例、局部变换、接口对、连接类型、约束 | 判断是否允许连接，不能用“相邻”代替关节 |
| 行为 | 滚动、转向、驱动、制动、骑乘等白名单插件 | 执行引擎已经实现并验收的能力 |
| 蓝图与实例谱系 | 设计版本、实际材料批次、加工/装配/拆解事件、世界实例 | 保存作品与双向追溯，不猜填历史 |

保持现有 Three.js、ES modules 与 `GameState`，逐项抽出模块，不立即改为 ECS、图数据库或后端。现有 `game-data.js` 是物品/配方入口，`game-state.js` 执行库存和保存事务，`world.js` 管表现与运动，`main.js` 做协调。

## 3. 类型与实际来源分开

“木板通常怎样生产”属于类型知识；“这块木板实际从哪里来”属于实例来源。

- 正常加工：记录实际投入、工艺版本、输出批次。
- 初始赠品：记录 `initial-gift`，加工历史为未知，不能补写“玩家锯过木头”。
- 新区宝箱：记录 `encounter`、世界种子、区块和发现 ID；宝箱发放现成物品，不证明玩家完成加工。
- 可选答题补给：记录人为发放原料，不把答题解释为物质生成。
- 旧存档：历史未记录部分标为 `legacy-unknown`，保留原库存/作品。

当前新区已经保存一次领取记录，但还没有每份材料的批次谱系。因此以上来源事件是后续设计，不能宣称当前背包已能追踪每一块木板。

双向查询目标：

1. 从作品查部件、材料批次、实际加工和关联知识。
2. 从某条知识查使用该规则的工艺、部件类型、蓝图和世界实例。

类型知识引用不等于真实发生过某次加工。

## 4. 最小数据契约

以下字段为拟议契约，不是可导入当前 v1 的存档。

```js
// 内容类型库：定义能力，不保存某个玩家的作品。
partType = {
  id, version, name, materialTypeIds, processTypeIds,
  knowledgeIds, modelId, collider,
  ports: [{ id, kind, localTransform, allowedConnectionTypes }],
  requiredCapabilities, supportedModes
};

// 蓝图：可以分享的设计；不复制库存或世界领取记录。
blueprint = {
  id, version, catalogVersion, mode, title,
  parts: [{ id, typeId, typeVersion, localTransform }],
  connections: [{ id, a: { partId, portId }, b: { partId, portId }, type }],
  requestedCapabilities, validationStatus
};

// 实例：实际制造出来的一件作品。
assemblyInstance = {
  id, blueprintId, blueprintVersion, worldTransform,
  partInstances: [{ id, blueprintPartId, materialBatchIds, originEventIds }],
  pluginSnapshots, riderState
};

// 谱系事件：只记真实提交过的事务，重试不能重复记账。
originEvent = {
  id, transactionId, kind, clockElapsed,
  inputBatchIds, outputBatchIds, processVersion, sourceRef
};
```

接口 `kind` 区分固定连接、转动轴、转向轴、动力输入与骑乘点。类型白名单、可用占位和限位由规则检查，不能仅凭模型碰在一起就认定有效。上述属性值应来自后续内容核查与实际插件；这里不猜填材料强度或关节参数。

## 5. 行为插件与提交顺序

插件注册由程序控制，不允许蓝图提供任意 JavaScript、`eval`、可执行 URL 或任意模块导入。

拟议接口：`validate(graph, catalog)`、`create(instance)`、`step(dt, input, environment)`、`snapshot()`、`restore(data)`、`dispose()`。状态快照必须独立校验，不保存 Three.js 对象、DOM 或函数。

事务顺序：

1. 校验蓝图大小、类型/版本、ID 唯一性、有限变换、接口和连接。
2. 校验请求的能力是否已实现、模式是否允许。
3. 校验库存和工艺条件，预览不扣料。
4. 生成可执行计划，再一次提交消耗、实例与谱系事件。
5. 通知表现同步；失败不部分扣料或留下半件实例。

插件销毁清理模型专用几何、监听和临时对象，共享资源不能随意释放。运动使用受限步长；暂停、隐藏、离线不补算。测试必须在独立世界进行。

## 6. 自行车必须补齐什么

| 能力 | 最小可观察验收 | 当前缺口 |
| --- | --- | --- |
| 轮轴 | 轮绕轴转，不从车架分离 | 木球滚动不能直接替代轮轴约束 |
| 车架与连接 | 装配后各部件保持相对位置，碰撞无重叠爆炸 | 无装配连接图或结构求解 |
| 转向 | 转车把后前轮与行进方向响应，限位可见 | 无载具转向 |
| 动力/传动 | 踩踏输入经明确简化传给驱动轮 | 无曲柄、链条/齿轮工艺与传动插件 |
| 制动 | 松动力后滑行，主动刹车减速且能停 | 无载具制动 |
| 骑乘 | 上下车、坐姿、输入切换、出入口占用检查 | 游泳姿态不能替代骑乘系统 |
| 稳定与地形 | 转弯/坡道响应明确，自动平衡须标游戏辅助 | 未选两轮/辅助轮/三轮试点 |
| 碰撞与回收 | 不穿墙、不进入未开区、可安全退出与回收 | 现有角色/球碰撞不足以直接支持整车 |
| 保存与拆解 | 重载保留装配与必要运动状态；拆回真实部件 | 无蓝图/装配实例与拆解政策 |

两轮自行车、辅助轮自行车和三轮车的稳定机制不同，首个骑行试点尚未选择。若采用自动平衡，必须明确是游戏辅助，而非现实两轮静止就能自行稳定。

不能为完成名词而直接添加“几块木板 → 金属链条/轴承/轮胎”的假配方。新材料与工艺先核查，再建立普通获取/生产路径；宝箱只能提供可用补给，不能成为唯一必需部件来源。

## 7. 拆解、迁移与分享

装配拆解通常返还实际部件；不可逆加工不能反向恢复原材料，例如烧成砖不自动回到湿黏土。破损、老化与损耗是将来需明确的规则，不在本轮添加离线损失。

现有主 key 和 v1 世界继续保留。增加装配域时，旧存档默认空装配和未知来源；先原文备份、转换、校验、读回，再写入。缺失插件或不兼容版本应保留可恢复原文与作品草稿，禁止静默删除。

离线蓝图导出只包含设计、类型版本和模式，不带领取记录、库存、账号或位置历史。导入先预览和校验，制造仍消耗本地真实库存。线上模型分享、账号与权限尚无实现，本设计不授权引入儿童数据收集。

## 8. 后续分段验收建议

1. 可拆轮轴组件：拖部件连接 → 推轮 → 轴约束可见 → 拆解/存档恢复；先验证部件接口与事务。
2. 骑乘载具：在明确选定稳定机制后，上下车 → 转向/驱动/制动 → 障碍/边界 → 暂停/重载。
3. 蓝图复用与谱系：改装保存 → 从知识查作品、从作品查材料 → 导出/导入设计，不复制奖励。

这是依赖顺序建议，不是已批准的新三项实现或工期。目标平板的部件数量、活动载具、关节和碰撞预算需实测后制定，不能照搬桌面数字。

本轮交付边界：完成链路、数据契约、执行/保存原则和自行车缺口设计；未制作自行车。儿童对工坊图示的理解、实际设备性能和骑行手感仍需真实试玩。
