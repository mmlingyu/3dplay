# 场景化创作实验室：完整设计与技术方案

状态：设计稿，待评审；未开始实现。本方案把“输入想法、画图、分析部件和材料来源、拼装实验、输出到场景、返回实验室拆解重装”设计成一条可执行闭环。它承接已有轮轴试装台，但不把演示台误称为作品装配、车辆或持久化系统。

日期：2026-10-15

## 1. 目标与设计原则

### 用户目标

孩子先表达想造什么，再画出自己的想法；系统将草图转成可讨论的部件建议，列出要用的材料、加工路线和河谷中的普通取得地点；孩子在实体工作台拼装，得到一个可观察、可操作的试验物件；带到河谷中试用后，能把同一件物件送回实验室拆开、修改和重新组装。

### 必须保持的项目原则

- 仍是同一个持续保存的开放世界。实验室、材料点、试验场都在河谷中，以场景目标进入，不新增脱离世界的主菜单式流程。
- 采集、加工与组装是主要玩法。每种必需材料都要有普通来源和正常加工路径；答题只提供可选补给，不成为工具、地图、作品或游玩时间门槛。
- 真实知识、游戏约定和幻想分别标记。不能把方块配方、游戏辅助稳定或简化物理说成完整现实规律。
- 草图是孩子的表达，不是系统自动下结论的工程图。部件和行为必须由孩子确认；不认识的想法保留为草稿。
- 试摆不扣材料；确认制作才提交。拆装不得复制部件或重复返还材料。
- 暂停、隐藏页面与离线不推进实验；可随时回到河谷。持久化上线后，不能让已确认作品只存在于易丢失的临时画布。
- 不接入儿童实时 AI 对话、外部模型 API、账号、云同步或遥测。AI 不是本方案的分析运行时。

### 设计目标

首要目标不是“识别任意画作并自动造出任何东西”，而是建立一个可扩展的创作闭环：草图能被表达；系统能解释自己建议了什么；孩子能改；可用材料能被找到；已实现的部件能真实连接；已实现的行为能被验证；不能实现的部分不会被伪装成成功。

## 2. 现状与方案边界

| 现状 | 对本方案的影响 |
| --- | --- |
| `src/world.js` 中场景物件通过 `target()` 注册，`src/main.js` 的 `interact()` 处理走近、采集、实验与面板。 | 新的想法桌、实验室、资源源点和作品应先成为场景实体目标。 |
| `src/workshop-3d.js` 是随打开/关闭创建与清理的实体近景；试摆在 `src/workshop-session.js`，正式合成仍由 `GameState.craft()` 处理。 | 可复用“近景操作、临时预览、事务提交、关闭释放资源”的边界，但不能把机械连接塞入现有格子配方。 |
| `src/axle-session.js` 与 `src/axle-3d.js` 可装拆两个轮子并分别旋转；试装件不扣料、不保存、不属于作品。 | 它是关节规则的概念验证。后续须替换为内容目录定义的正式组件实例和工作台连接图。 |
| `GameState` 集中管理库存、规则和本地保存；当前 `version: 1` 校验严格，材料是数量表，未保存逐件来源。 | 作品数据需进入状态层并具备迁移、备份和严格校验；不能在 Three.js 对象上私自保存。 |
| 角色自动走近是直线趋近，障碍可能挡住。地图是有限区块。 | 采集地点要给方向/位置提示并保留摇杆，不能承诺点击后总能自动绕障抵达。作品也不能穿墙、越过未开区域或占用受保护位置。 |
| 项目沿用 ES modules、回调、状态订阅和 `mutate()`；当前没有 EventBus/ECS。 | 采用领域分层，但保留现有协调方式，不为此方案重构全项目架构。 |

本方案分清三层“来源”：

1. **类型级来源说明**：某材料可以在哪个普通场景点采集、通过什么已核实配方加工。这是当前需求必需项。
2. **作品部件用料**：一件部件用了哪些材料及数量。这是完成装配和拆解账目的必需项。
3. **逐份材料批次谱系**：哪一次采集、宝箱或加工产生的具体材料进入了哪个部件。这是更完整的双向谱系能力，不是当前数量型背包已有能力。建议作为独立后续范围，不能在没有批次数据时伪造历史。

## 3. 场景与孩子操作流程

### 河谷场景动线

```text
想法桌/画板
    ↓ 生成草稿卡和部件建议
采集点 / 现有工坊 / 新增部件制作台
    ↓ 找齐材料并取得正式部件
实体装配台
    ↓ 校验连接，运行桌面试验
试验场（河谷中的空旷区域）
    ↓ 测试滚动、转向、承载等已支持行为
回到同一实验室
    ↓ 原型归还、拆件、改图、重装
存档与下次继续（持久化里程碑）
```

所有入口都由场景中的对象触发。面板只负责当前对象的近景操作，不出现一个要求孩子依次填写十几项的“创作配置表”。

### 阶段 A：输入想法

孩子走近“想法桌”，看到一张空白小卡和简短提示，例如“你想造什么？”。首版允许短文本输入；键盘不是唯一入口。语音可以作为后续可选输入，但须先实测设备浏览器支持，并明确是否调用系统/网络语音服务；未确认隐私与设备行为前不启用。

建议把草稿标题设为可选、短输入。系统不得因为孩子没写标准名称而丢弃想法。示例“想造一辆能骑的车”保存为用户原话；不改写成系统认为更“正确”的东西。

### 阶段 B：画图板

走到实体画板后进入画板近景，优先支持手指/触控笔自由画、撤销一步、橡皮、少量颜色、清空前提示、完成/返回。画板采用向量笔画保存，而非高分辨率贴图，以便平板缩放、存档与重绘。

建议加一排可拖到画布上的“部件贴纸”（例如轮子、杆、板、座位）作为明确的结构提示。自由笔画表达外观；贴纸是孩子主动给系统的结构线索。系统分析只信任已确认的贴纸/选择，不尝试从任意像素推导工程尺寸和连接。

### 阶段 C：系统给部件和材料建议

完成画图后打开“想法拆解台”。系统给出少量大图卡：建议的部件、数量、它们大致接在哪里、已支持的动作、材料总量及普通取得地点。每项可“保留”“换一个”“先不做”。孩子能回画板改图，也能保留不完整草案。

每个材料卡显示：

- 需要数量、已有数量、还差数量。
- 该材料在河谷中的普通采集位置或有效制作配方。
- 加工品的前置原料和加工步骤，例如“木料 → 木板”。
- 这是“现实材料说明”“游戏约定”还是“幻想作品”。

点材料地点只设置场景方向提示/目标，不传送角色、不跳过采集；自动走近受现有寻路能力限制，失败时可手动走。找不到正常来源或可信加工链的必需材料，标记为“还没有普通取得办法”，不让宝箱成为唯一来源，不继续显示“可以制作”。

### 阶段 D：实体拼装

到“部件制作台”得到正式部件后，再到“装配台”拼整体。桌面由可拿取部件托盘、带编号/图形提示的接口、中央装配架、结果转台组成。把部件拖近对应接口时显示：

- 绿色：接口匹配，可吸附。
- 红色：接口不匹配，松手退回并给一句具体说明。
- 黄色：连接有效，但作品缺部件或行为尚未支持。

点已装部件可取下，拖动整体可旋转查看；提供至少 44×44 CSS 像素的按钮备用操作。试摆期间不扣材料。只有所有必需的部件、接口和所请求的已实现能力均通过校验，才能点击“完成试装”。必要材料在部件制作的确认事务中扣除，不能在打开工作台或拖动预览时扣。

### 阶段 E：输出试验物件并在河谷测试

“完成试装”建立一个唯一的 `assemblyInstance`，放到试验区的合法空地。试验区可以是现有可走地面上的标记区域，不要求另造一个独立关卡。出场前校验地图范围、已开放区、建筑占位、障碍、水域和安全交互空间。

靠近作品出现上下文动作，例如“试一试”或“送回实验室”。行为仅由程序白名单插件提供。物件具有视觉形状但没有对应插件时只能预览，不得宣称可骑、会转向或能承重。

### 阶段 F：回实验室、拆解、重装

走近同一个试验物件并选“送回实验室”，或在实验室选择“召回试验物件”。这是移动同一 `instanceId`，不是复制。作品状态从 `in_world` 变为 `in_lab`，清理场景碰撞体/模型引用后，由装配台重建表现。

拆解图按连接树显示父件、子件和接口。取下某部件时，该 `partInstanceId` 只能有一个所有者：在装配中或在可用托盘，不能两处同时存在。允许重复装回同一部件；不把可拆组件变回未加工原料。不可逆加工、消耗品或未来损坏损耗必须有明确规则；本期建议无损实验，所有可复用部件完整返还。

“重新试验”创建新的实验记录或覆盖该作品的可见“上次结果”，不创建第二件物件、不重复扣料。关闭面板回到世界时持续保持原型位置和装配状态；到持久化里程碑后，刷新与重载也要恢复。

## 4. 分析器设计：规则建议，孩子确认

首版不做视觉模型，也不让自然语言直接生成代码。`IdeaAnalyzer` 的输入是：用户原话、草图笔画、孩子主动放置的部件贴纸、孩子确认的动作图标、目录版本。输出是可解释的候选项，不是执行命令。

示例：

```text
用户原话：我想造一辆能骑的车
孩子确认的动作：可以向前走、可以转方向
画板贴纸：两个轮子、一个座位（候选，不当事实）
系统建议：车架、轮轴、轮子、座位、转向接口
缺口：所需车轮/车架类型或材料链如果尚未实现，就明确显示“暂未支持”
```

分析结果分四类：

- `supported`：目录、材料与行为都存在，可进入制作。
- `needs_materials`：规则有效，但数量不足；显示普通来源。
- `needs_design`：外形/连接或孩子意图还不明确，询问一个具体、可视的问题。
- `unsupported`：缺少部件、来源、真实加工链或行为插件；保存草图，不输出可执行作品。

分析器可用有限规则：动作到能力映射、部件模板、部件依赖关系、接口兼容表和材料递归清单。每条建议携带解释 ID 和来源；不是根据“AI觉得像什么”静默添加材料。以后若要接模型，必须另行确定儿童数据、服务、适龄和家长授权，模型只能产候选、不能写入规则或执行代码。

## 5. 内容目录和数据契约

### 内容目录（只读定义）

新增内容目录与现有 `ITEMS`/`RECIPES` 的边界建议如下：普通材料和既有配方继续以 `src/game-data.js` 为准；可拆部件、连接口、部件模板、能力和来源引用放在独立的创作目录模块。不要先把所有引擎重写成知识图数据库。

```js
componentType = {
  id: 'part-type-id',
  version: 1,
  label: '儿童可读名称',
  modelId: 'allowlisted-model-id',
  ports: [{
    id: 'port-id',
    kind: 'revolute',
    localPose: { position: [0, 0, 0], rotation: [0, 0, 0] },
    accepts: ['matching-joint-kind'],
    maxConnections: 1
  }],
  materialPlan: [{ itemId: 'existing-item-id', count: 1 }],
  processRecipeIds: [],
  sourceIds: ['world-target-id'],
  capabilities: ['only-registered-capability-ids'],
  truthMode: 'simplified',
  knowledgeRefs: []
};
```

`truthMode` 限定为 `reality-grounded`、`game-simplification`、`fantasy`。`modelId`、`capabilities`、`sourceIds` 和工艺 ID 都在代码白名单中解析；存档不得指定任意 URL、模块路径、材质 shader 或函数。

草稿保存原话与用户画面；蓝图保存抽象设计；部件实例保存实际部件与用料；作品实例持有部件 ID、连接和世界状态。这四者不能混成一个 Three.js Group 或单个配方结果。所有 ID 全局唯一；所有引用必须能解析。删除草稿不能偷偷删除已有作品所引用的蓝图版本。

材料来源先按内容目录做类型级关联；实际作品记录每个部件确实消耗的材料类型和数量。逐份材料批次、采集事件、加工事件及双向知识谱系可在用户明确纳入范围后增加事件账本，不能从旧数量库存倒推历史。

### 连接规则

- 端口以局部坐标、连接类型、方向/限位和最大连接数定义。外观碰撞不代表连接。
- 连接校验包含端口存在、双方类型兼容、双方容量未满、变换有限、部件实例未被别处占用。
- 蓝图必需的部件图必须连通到根部件；环路只在明确支持的关节类型中允许。
- 简化版不做通用应力/梁结构求解。只执行显式定义的连接约束与插件。
- `revolute` 仅表示可绕指定轴转动；不会自动带动另一个轮子。传动需另一个明确的耦合插件。
- 对缺件、错接、超量、越界和不兼容版本要返回儿童短提示及供家长/调试使用的结构化错误码。

## 6. 材料计划和来源解析

`MaterialPlanner` 递归展开部件的输入物料与可用加工配方，直到到达可采集基础物料。结果是一棵材料依赖树，不是文本猜测。

```js
{
  requirements: [{ itemId, required, available, missing }],
  steps: [{ recipeId, inputs, output, batchCount }],
  sources: [{ itemId, targetId, worldName, sourceKind }],
  status: 'ready' | 'needs-materials' | 'no-valid-source'
}
```

规则：

1. 每个叶节点必须指向已存在的普通采集点，或指向能继续展开的有效配方。
2. 配方展开必须检测循环、未知 ID、零/负数量和无法生产的输出；循环或断链立即显示未支持。
3. `available` 只用于显示库存状态，规划过程不得改库存。
4. 取得材料仍走现有普通采集/工坊；不能给自行车独占一个宝箱材料或要求答题。
5. 找来源优先展示“去哪里”与地图方向；当前直线自动走可能被阻挡，手动路线始终可用。
6. 没有核实的橡胶、金属件、车轮、链条等材料 ID 和加工链时，不得为了让自行车界面显示绿色而添加假配方。内容负责人先确认真实简化方式、常规来源与说明，再进入目录。

## 7. 事务、原型运行与拆装

### 制作事务

预览和放置组件是临时状态；确认制作时执行一个原子状态变更：

1. 校验目录版本、蓝图结构、能力、数量、库存与总数上限。
2. 计算完整成本，不在逐件扣料过程中暴露半完成状态。
3. 为本次 `transactionId` 检查是否已提交，防止双击/重试发两次。
4. 一次 `GameState.mutate()` 扣材料并创建部件实例或装配实例。
5. 状态保存失败时提示“本次未能安全保存”，保留可导出/恢复路径；UI 不谎报成功。

桌面双击、触屏拖动、面板重绘、网络/存储异常都不能造成重复消耗或重复发件。游戏无后端，但重放同一事务 ID 仍应由状态层拒绝。

### 行为插件与试验

插件只由程序注册，不运行蓝图内代码。建议接口：

```js
validate(assembly, catalog)
createRuntime(assemblySnapshot)
step(dt, input, environment)
snapshot()
restore(snapshot)
dispose()
```

插件输出纯数据快照，不能把 Three.js、DOM、回调、任意模块路径放入存档。场景对象由表现层根据快照创建。没有能力插件的作品只能观察或标记为“还不能试这个动作”。

现有 `main.js` 可见帧运行规则要求页面隐藏时不推进。原型运行建议使用有限固定步长累积器、限制单帧最大步数，暂停、隐藏、返回实验室时清零输入并停止模拟。首期不引入通用刚体物理引擎：只为被批准的行为编写小型、可测的运动规则。稳定、碰撞、最大速度等参数集中在规则配置，不散落到渲染代码。

### 试验物件入场与回收

在河谷创建原型前运行单独的 `prototypePlacementProblem()`，检查：

- 角色/目标位置在已开放地图内；不越地图边界和连续区块边界。
- 原型包围盒不与地形、公共设施、建筑、树木、角色出生/通道等冲突。
- 有完整输入/退出空间，角色能离开试验物件。
- 水面、斜坡等只在对应插件明确支持时接受。

作品入场不调用普通 `placeBlock()`，不写入方块 `blocks`；场景实例由 `RiverWorld.syncAssemblies()` 单独维护。场景同步必须可重复调用，不重复创建网格、碰撞体或标签。

回收时先将 assembly 状态变为 `in_lab`，保存世界位置/实验快照，然后移除场景实体。若状态提交失败，不删场景中唯一的一件作品。拆解事务按部件 ID 把 owner 从 assembly 原子改为 available；重复拆解同一个连接必须失败且不增加部件数量。

## 8. 建议模块与现有入口

保持项目已有模块风格，不一次性改造为 EventBus/ECS。

| 拟议文件/职责 | 对应现有入口 |
| --- | --- |
| `src/creation-data.js`：部件类型、部件模板、连接兼容、动作白名单、材料规则与来源引用。 | `src/game-data.js` 管普通 ITEMS/RECIPES；新内容不要覆盖其职责。 |
| `src/creation-session.js`：短期画图编辑、候选确认、装配预览和当前步骤，不直接扣库存。 | 类似 `WorkshopSession`，纯领域状态、可独立单测。 |
| `src/creation-rules.js`：草稿校验、配方展开、连接图校验、场景落点校验。 | 规则保持可脱离 DOM/Three 单测。 |
| `src/creation-3d.js`：画板/托盘/接口/转台的近景交互、射线拾取与高亮。 | 参考 `workshop-3d.js`、`axle-3d.js` 生命周期。 |
| `src/creation-runtime.js`：白名单行为插件装配、步进、快照与清理。 | `RiverWorld.update()` 调用；不另建常驻 RAF。 |
| `src/world.js`：想法桌、实验室、材料源点目标；原型实例增量创建、拾取、碰撞和移除。 | 复用 `target()`，装配物件与格子方块、木球分开管理。 |
| `src/game-state.js`：库存事务、唯一实例 ID、存档验证、迁移、拆装记账。 | 现有 `mutate/save/notify` 单一提交入口。 |
| `src/panels.js`：`idea`、`drawing`、`analyze`、`assembly` 等可访问近景路由。 | 接口延续 `createPanels()` 和显式 `dispose()`。 |
| `src/main.js`：场景交互分派、角色走近、面板状态、实验输入路由。 | 保留主循环；面板打开时停止玩家控制，不应意外停止合法的游戏时间规则。 |

所有几何/材质/纹理有明确所有者：会话创建则会话销毁，共享缓存则由缓存统一释放。关闭、切换模式、页面隐藏、尺寸变化和连续打开关闭三次都须清理渲染循环、ResizeObserver、事件监听、捕获的指针和临时网格。画板和装配近景优先复用一套渲染器生命周期抽象，而不是每个页面留一个常驻 WebGL 上下文。

## 9. 状态流转和失败回退

```text
idea
  └─ editDrawing
       └─ analyze
            ├─ unsupported → keepDraft / returnToDrawing
            ├─ needs-materials → collectOrCraft → analyzeAgain
            └─ ready → assemble
                         ├─ invalid → repair / removePart
                         └─ valid → commitPrototype
                                      └─ inWorld
                                           ├─ experiment
                                           └─ returnToLab
                                                └─ disassemble / reassemble
```

每个步骤都支持回退，不要求先采齐所有材料才能保存草稿。错接、缺料、场景落点冲突、插件缺失、存储失败均给可恢复状态；失败操作不可扣料、丢原型、消耗领取记录或删除旧存档。长提示放在可展开说明中；儿童常用反馈限制为一个短句、图示和可直接执行的下一步。

## 10. 存档与旧世界兼容

存档上线属于用户原先指定的最后阶段，需先独立验证完整迁移设计。建议将创作域并入唯一的 `GameState`，而不是 `localStorage` 第二套互不协调的作品存档：

```js
{
  version: 2,
  // 保留 v1 的 inventory / blocks / player / toys / clock /
  // flora / land / garden / kiln / chests / settings / stats 等数据
  creation: {
    schemaVersion: 1,
    nextId: 1,
    drafts: [],
    blueprints: [],
    partInstances: [],
    assemblies: []
  }
}
```

建议的主键策略：新存档使用 `yuanyuan-river-valley-v2`，保留当前 `yuanyuan-river-valley-v1` 不动。加载优先读取有效 v2；没有 v2 时读取并验证 v1，经纯函数 `migrateV1ToV2()` 补空的创作域。迁移必须：

1. 先保留旧 v1 原始 JSON（不把对象重新序列化当成“原文备份”）。
2. 生成 v2 候选状态并全量校验；原库存、世界坐标、建筑、球、时间、植物、区块和领取记录逐项比对保持。
3. 写入新 v2 key 后读回并再次校验，只有成功才切换本地活动存档到 v2。
4. v2 写入失败或超出浏览器配额时继续保留并使用旧 v1；提示用户导出，不删除任一版本。
5. 迁移再次运行必须幂等，不能再发初始材料、重复创建作品或覆盖备份。

每个创作域还有独立 `schemaVersion` 和 `catalogVersion`。内容目录升级导致部件类型不再支持时，存档保留原草图/原始部件 ID；可回退成只读剪影和“当前版本不能继续模拟”的说明，不静默删除、换成别的材料或执行旧插件。

LocalStorage 容量有限。画笔用归一化向量坐标，限制 stroke 数/点数/部件数/蓝图数/活动原型数，限制值集中于 `CREATION_LIMITS`；实际默认上限须在目标平板和典型世界测量后确认。超过上限时先解释并允许导出，不能截断存档后声称全部保存。首版不引入服务端或云同步。

用户最新要求包含“再返回实验室拆解、重新组装”；拆装交互会在会话阶段先实现和验证，但必须到存档阶段才承诺刷新/重载后继续同一个原型。持久化未交付前，测试页面要明确标记“实验草稿暂存在本次打开期间”，不能用于真实长期儿童作品。

## 11. 首个试验作品与稳定规则决策

轮轴试装台已经证明左右转动接口可以独立更新，但不具备真实材料来源、车架、驾驶、碰撞、承重或作品存档。它不能直接升级成“自行车已实现”。

如果以孩子提出的自行车作为首个行为样例，建议先设计：

- 车辆类型：双轮自行车造型。
- 稳定方式：`assisted-upright` 游戏辅助模式，车辆移动时将横滚角限制为 0，低速/停止也保持直立；不是现实自行车的自然静态稳定模拟。
- 反馈：车辆旁持续显示“游戏辅助扶稳”，长说明说明现实自行车的平衡与速度、转向等条件有关，当前没有完整模拟。
- 控制：前进/停止、左右转向、刹车、上下车，先以有限速度和受控方向验证；未实现真实链条/齿轮动力前，不显示“踩踏传动已模拟”。
- 边界：碰撞停下或温和阻挡；不翻滚惩罚、不跌落地图、不进入未开放区；可随时下车和回收。

这是本方案的推荐实现选择，不是用户已确认的稳定机制。另一个更贴近“静止仍有几何支撑”的选项是三轮车；它的稳定解释简单，但与原先“自行车”意图不同。进入载具开发前须由产品负责人确认采用双轮游戏辅助、三轮构型，或其他方案。

材料方面，当前 `ITEMS` 没有专用轮胎、金属轴承、车架管材、链条或刹车件，也没有相应来源和加工链。不能将木板直接配成金属件。进入正式自行车制作前，内容设计需逐项确认：

1. 哪些部件用已有材料可合理简化，哪些必须新增真实材料类型。
2. 每种新增基础材料的普通采集来源，不能只靠奖励箱。
3. 现实材料如何加工成可用部件；需要工具/条件时一并核实。
4. 哪些是幻想模式或教学占位，界面明确分开，不共享“现实模式”标签。

材料路线未完成时，分析器保留车的草图并显示缺口；可先做无材料扣除的技术演示，但不能把它当作已完成的儿童作品链路。

## 12. 分阶段实施计划

每阶段都形成可单独评审的里程碑；本文件本身不授权自动开始任何一个阶段。

### 阶段 0：内容与交互规格冻结

- 核验一个纵向样例需要的部件、材料事实、普通来源和加工条件。
- 选定画板的文字/触控操作、语音是否完全排除首版。
- 确认未知部件保留方式、实验中允许/不允许的行为。
- 在车辆开发前选稳定规则。暂不更改物品表或主存档。

通过条件：产品规则、知识来源、游戏约定和待验证项均有清单；不存在“没有常规来源但仍标为可制作”的必需材料。

### 阶段 1：场景想法桌与向量画板

- 在河谷新增可走近交互的想法桌和画板。
- 保存想法原文、有限笔画、撤销/清空、部件贴纸和返回。
- 第一期草稿暂用内存会话或开发测试数据，不宣称刷新可恢复；若决定真实儿童可用，持久化须提前进入本阶段验收。
- 测量画板首次进入、画一条线、撤销、完成、返回是否可独立操作。

通过条件：桌面/平板均可绘画、撤销、退出；取消不会修改背包；长时间笔画受上限约束；关闭后无 WebGL/事件泄漏。

### 阶段 2：规则分析与材料路线

- 建立版本化部件目录、连接类型、能力白名单、来源 ID 与知识说明。
- 实现确定性 `IdeaAnalyzer` 和递归 `MaterialPlanner`。
- 分别测试支持、缺料、缺配方、错连接、未知行为和未知部件。
- 从草图返回修改不会丢失原话与画面。

通过条件：同一输入/目录永远得到同一候选；每条材料建议能追到已存在的来源或有效加工规则；缺来源不允许“已准备好”。

### 阶段 3：正式部件和实体装配试验

- 将轮轴概念试装提升成正式、可复用的部件类型和关节图，不再使用无材料演示件冒充背包物品。
- 实现部件制作预览/原子确认、装配会话、端口吸附、红绿有效性、取回和连接图校验。
- 首先通过一件真实有来源的部件组合验证连接/拆解，不要求立即完成整辆自行车。
- 物品来源、组件材料与失败退回均不得产生重复扣料。

通过条件：同一轮子只能有一个所有者；空库存/错口/重复确认均不改变材料；有效轮轴连接后单轮旋转符合定义；拆开后原 ID 原样返回。

### 阶段 4：原型进入河谷、行为实验、返回重装

- 建立 `assemblyInstance` 与独立于格子建筑的场景表示。
- 支持合法落点校验、实验输入、有限插件、回实验室、按图拆装和迭代。
- 首次先测 3D 表现、边界/碰撞和暂停，不同步扩展通用刚体物理。
- 本阶段若未完成持久化，只限自动化和成人开发验证；面向儿童开放前必须先保证草稿与作品可保存。

通过条件：输出/回收同一实例不复制；一个试验物件最多一个场景实体/碰撞体；暂停/隐藏不推进；插件快照不含 DOM/Three.js 对象；重进实验台释放并重建资源正常。

### 阶段 5：可骑载具与明确稳定规则

- 以已确认的部件来源、接口和稳定模型实现上车/下车、前进/转向/制动及场景阻挡。
- 在车辆和帮助说明中显示真实/游戏简化边界。
- 只有已验收的能力才进入可执行蓝图；乘坐、碰撞、速度、旧场景输入等全部有验收用例。

通过条件：孩子能看到稳定模式提示；已实现输入方向和行为一致；未实现的传动/承重不显示为完成；边界阻挡后可正常下车和回收。

### 阶段 6：作品保存、重载、拆解与兼容迁移

- 按第 10 节实施新的版本化 schema、v1 → v2 转换、原始 v1 备份和读回校验。
- 保存原话、画面、蓝图修订、部件实例、连接、作品位置、有限运行快照和实验记录。
- 加入重复事务防重、损坏/未知类型降级恢复、失败导出、跨版本部件行为边界。
- 完整验证“重载后回到同一作品 → 拆解一次 → 材料/部件数量正确 → 改装 → 再保存和重载”。

通过条件：有效旧世界不丢建筑、物资、球、时间/季节、开垦/领取和园地；升级失败仍可使用/导出旧世界；非法导入不替换当前世界；重复拆解/提交不能多发材料。

## 13. 验收与测试矩阵

### 纯规则测试（Node `node:test`）

- 材料树：有效递归、未知配方、循环、来源丢失、库存缺额、数量上下限。
- 草稿：空画布、撤销、超限点数、越界坐标、无效色值/工具与重放一致性。
- 蓝图：未知部件/版本、重复 ID、缺端口、错类型、端口超载、孤立部件、越限部件数、插件未注册。
- 所有制作事务：材料不足、双击同事务、存储失败、校验失败时无部分扣料/发件。
- 装配与拆解：实例唯一性、所有权守恒、拆回完整、不重复返还、改装后的图匹配。
- 地图落点：未开放区、受保护设施、建筑/水面/边界冲突和正常空地。
- 迁移：代表性的当前 v1 存档字段逐项保持；无扩展的旧存档默认空创作域；损坏 v1 与配额失败保留旧原文。

### Playwright 浏览器集成

- 开独立 BrowserContext，禁止访问/清理真实用户存档。
- 按场景路径：走近想法桌 → 输入/作画 → 生成可解释分析 → 看材料源 → 进入工坊 → 装配 → 场景实验 → 回实验室 → 拆装。
- 桌面鼠标、触屏指针、窄屏竖屏、平板横屏；按钮目标 ≥44 像素；对触摸取消、第二指、画布外松手、失焦、隐藏、面板切换分别断言。
- 键盘 Tab 顺序、焦点循环、Esc 返回、按钮可读名称、颜色不是唯一有效/无效标记。
- 场景物件与普通方块、球的拾取/碰撞互不误触；高亮、标签和源点导航不会遮住摇杆/底栏。
- 面板打开/关闭/重复三轮、不同画板大小/方向变化、渲染器资源释放；无页面异常和重复 Canvas。
- 存档：完整作品保存→刷新→找回→拆解/重装→保存；注入存储失败并确认原档不变。

### 性能和真实试玩

桌面无头 Chromium 的 SwiftShader 结果不替代真实平板性能。先选定实际平板型号/系统/浏览器，再测完整河谷与装配近景在代表性蓝图下的帧率、GPU 内存、主线程操作反馈、绘制点数上限和长时间发热。WebGL 设备恢复、页面隐藏再现与旋转屏幕都需测。

儿童试玩记录“是否知道下一步、是否能修改/返回、错误时是否知道怎么做”，不记录为学习成绩。分别测试无补给奖励时的普通材料路径、阅读困难时的图示路径、作品失败后的恢复。不能用停留时长、正确率或自动测试通过宣称学习效果。

## 14. 配置、资源与性能约定

- 新规则的坐标、阈值、草图大小、端口拾取半径、最大装配部件数、插件步长统一放入创作领域配置；所有初始值注明是待性能/试玩校准的实现默认值。
- 当前河谷 `RiverWorld` 保留单一持续场景渲染器；创作近景仅在打开时创建，关闭时严格释放。避免每个场景状态各留一个循环渲染器。
- 3D 试验先关闭阴影，复用材质和几何，实例化重复零件；不引入后处理或全地图动态刚体。
- 角色/载具物理与画布鼠标输入互斥；打开面板清空移动/转向输入，松手和取消保证状态还原。
- 所有动态对象可由纯数据快照重建。画图笔触不在逐帧 loop 创建 Three.js 对象。
- 背景物件和部件模板使用 GLB 或原创程序模型需单独评估；不能用占位几何假称最终资产，也不能下载未经许可的模型。

## 15. 未决事项与开工门槛

以下不影响本方案的架构成立，但必须在对应实现前确认：

1. 画板文字是否仅键盘，语音是否排除首版。默认建议：短文字可选，语音先不接入。
2. 材料链核查负责人及最终样例部件；当前没有车轮/车架/金属/橡胶来源链。
3. 首辆车用双轮“游戏辅助扶稳”还是三轮几何稳定。默认方案推荐双轮、清晰标注辅助规则以贴近原始自行车意图，但需明确批准后才能编码。
4. 原型最初放置范围与实验结果类型；默认只允许步行可到的河谷试验区，不加破坏性失败惩罚。
5. v2 存档迁移和本地储存容量实测；迁移程序确认前不改现有 v1 存档。
6. 绘图尺寸、蓝图数、部件上限和同时存在的原型数；根据目标平板实测再定，不以桌面机默认值冒充设备预算。
7. 是否要逐份材料批次追溯。默认首期显示来源和每件部件用量，批次级历史另立范围，避免为了“谱系完整”先推翻现有数量背包。

## 16. 方案完成判据

方案进入实现评审时，需同时检查：

- 孩子操作流程始终以河谷场景实体为入口，并允许返回草图/拆装。
- 部件、材料、加工、来源和能力之间有版本化引用，没有自由文本生成配方或可执行代码。
- 预览、制作、入场、回收、拆解的材料所有权与原型唯一性规则明确。
- 材料来源常规可取得，科学事实/游戏约定/幻想标记一致。
- v1 原世界兼容、迁移失败保留、存储失败恢复路径已通过设计审查。
- 每个里程碑有自动规则测试、桌面/平板浏览器流程和现实设备待验项。
- 内容未知或行为未实现时，产品仍能保留孩子的想法而不误导“已完成”。
